- Background Jobs library (org.openxtalk.library.async): asyncShell, asyncProcessOpen, asyncReadFile, asyncWriteFile, asyncAppendFile, asyncCopyFile and asyncListFolder run a shell command or a program, read, write or copy a file, or list a folder while the window stays live; each returns at once with a job's number and the calling object is sent a message when the job is done. asyncCancel, asyncStatus, asyncProgress and asyncJobs act on the jobs under way. shell(), open process and URLs are unchanged (#649)
- Tests: the test library's requirement "extension" skips a test where an extension it loads is not there, as in an Android standalone built by a release's IDE that has no such library yet (#649)
- Tests: a freeze meter (tests/lcs/extensions/libraries/async-freeze.livecodescript) writes to each run's output how long a stack's own messages stop during a shell command, a large file's reading, writing and copying, and the listing of a tree, with the blocking call and with a background job (#649)
- Extensions with native code: MCAsyncNativeCall has a C function of the extension's library called on another thread and sends a message when it has returned, and a wake (MCAsyncNativeWakeCreate, MCAsyncNativeWakeFunction, MCAsyncNativeWakeContext, MCAsyncNativeWakeDelete) lets a thread of the library's own tell the script that it has something, which arrives as one message however many times it was signalled; an extension binds to them with "<builtin>" ("Native code that takes time, or has threads of its own" in the Extending guide) (#649)
- Background Workers library (com.livecode.library.worker): workerStart starts a worker, the engine again with no window, that runs the handlers of a script while the stack goes on; workerCall calls one of them with any parameters (text, numbers, binary data, arrays) and returns at once, and the calling object is sent a message with the result or the error. workerSendProgress reports progress from a worker, workerStop stops one and the call it is running, workers and workerPending list them. In a standalone the worker is the application itself, which the library takes over before the application's own startup handler runs, so the library and the Background Jobs library must both be among its inclusions (#649)
- Background Database library (com.livecode.library.asyncdatabase): asyncDatabaseOpen opens a database connection that a worker holds, and asyncDatabaseQuery and asyncDatabaseExecute run a query or a statement there and return at once; the object that asked is sent a message with the rows (keyed by the columns' names) or the result, or revDB's error. A connection's requests run in the order they were made, and connections at the same time; asyncDatabaseClose ends one, with the request it is running. revDB's own calls are unchanged. On the desktop, with every database revDB has a driver for (#649)
- revdb: revGetDatabaseDriverPath gives empty when no driver path has been set, as in a standalone; it ended the engine (#649)
- Background Workers library: in a web standalone, workerStart starts a worker that is a web worker of the page, which loads the engine again with the standalone's files and runs the script's handlers while the page goes on; workerCall, workerSendProgress, workerStop, workers and workerPending work there as on the desktop. Before, a worker started in a browser ended at once with "not supported", as it still does on Android and in the web IDE. A worker in a browser has a file system of its own, and each is a whole engine, with as much of the browser's memory as the page's (#649)
- Web engine: an engine loaded in a web worker starts without a user interface, as "-ui" starts the desktop's: its stacks open without a window, and its waits give the worker's events a turn. Module.livecodeEngineURL is the address of the engine's script, recorded as it loads unless the page has set it. A page's engine is unchanged (#649)
- Background Database library: in a browser asyncDatabaseOpen still ends with "worker failed: not supported", now without starting a worker (#649)
- CI: tools/ci/web_workers_check.py runs workers in a web standalone in Chromium, Firefox and WebKit (web.yml): calls with text, numbers, binary data and arrays both ways, errors, progress, output, waits and messages in a worker, two workers at once while the page's timer goes on, stopping, a worker whose script quits, a script that does not compile, and the database library's refusal (#649)
- Background Jobs library: asyncEndWithParent has the engine end when the process it names ends, however that ends. A Background Workers worker does so from its start, whether or not it loads the Background Jobs library, so a busy worker no longer runs on after its stack's process crashes or is killed (#649)
- Background Workers library: on Windows a call no longer waits up to a quarter of a second to begin, and a large request through the worker's input takes a fraction of a second, not many seconds (#649)
- Background Workers library: a line a worker writes that begins as the library's own but cannot be read is the worker's output, as other lines are; it was dropped (#649)
- Tests: hardening tests for workers (extensions/script-libraries/worker/tests/hardening.livecodescript): replies arriving while a handler waits, chained calls, many workers at once, the same keys, large values both ways, a killed worker, a killed stack with busy workers, workers stopped as they start, and the input read as on Windows (#649)
