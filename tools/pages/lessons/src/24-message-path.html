The road a message takes

A message does not stop at the object it was sent to. If that object has no handler for it, it travels along the message path, through every object that holds it, until a handler answers it or it reaches the engine:

  1. the control it was sent to (the target)
  2. the group the control is in, if it is in one
  3. the card
  4. the card's background groups
  5. the stack, then its main stack, if it is a substack
  6. libraries and back scripts the program has added (Libraries shows how)
  7. the engine, which does its default job for messages it knows, and nothing for the rest

The first handler on the way runs, and the message stops there.

The button has no script, so the message went to the card. The card had a handler, so the stack's handler, further along, never heard of the click.

A handler for a message the engine itself acts on, such as keyDown or closeStack, stops that action unless it passes the message. A keyDown handler without pass keyDown means the field never gets the key.

The reverse is not true: the stack cannot call a handler that lives in a button's script by name, because the stack is not on the button's path. To run it, send the message to the button.

Where should a handler go?

  • In the control, when it is about that control alone: what this button does when clicked.
  • In a group, for controls that work together, like a set of tool buttons.
  • In the card, for what belongs to one screen: getting it ready in openCard.
  • In the stack, for anything the whole program needs: helper functions, saving, starting up.

The message path is one of HyperCard's big ideas, and it has hardly changed since 1987: button, card, background, stack, Home. In OXT-Beyond a HyperCard background becomes a group shared by several cards, and keeps its place on the path.
